## 二、需要提交的材料

登记为形式审查，材料齐备且格式合规即可受理。共四项：

| 序号 | 材料 | 本项目的状态 | 产出方式 |
|------|------|--------------|----------|
| 1 | 计算机软件著作权登记申请表 | 需在线填写 | 官网系统内填报，字段取值见 `申请表填写指引.md` |
| 2 | 申请人主体证明 | 需自备 | 个人：身份证复印件；单位：营业执照副本复印件 |
| 3 | 源程序鉴别材料（60 页） | **已可自动生成** | `tools/gen_source_doc.py` |
| 4 | 文档鉴别材料（用户手册） | **已撰写，待补截图** | `用户手册.md` + `tools/gen_manual_docx.py` |

### 2.1 源程序鉴别材料

登记要求：

- 提交源程序前、后各连续 30 页，共 60 页；不足 60 页则全部提交
- 每页不少于 50 行，不含空行与无效注释行
- 页眉标注软件名称与版本号，须与申请表一致
- 页码标注在右上角，连续编号
- 最后一页应是程序或某个模块的自然结束处
- 不得包含用户数据、接口密钥等敏感信息

生成命令：

```
python3 docs/copyright/tools/gen_source_doc.py \
    --name "论文精读辅助分析软件" \
    --version "V1.0" \
    --out docs/copyright/build/源程序.docx
```

脚本把「每页 50 行」做成固定排版结果而非依赖 Word 自动断页：按显示列宽硬折行、精确行距、逐页硬分页。生成后会打印实际页数与末页收尾的文件名。

已验证的输出特征：A4 纸张，60 页，每页 50 行，页眉左侧为软件名称与版本号、右上角为自动页码域，首页起始于后端服务入口 `backend/main.py`，末页收尾于一个前端页面组件的自然结束处（右花括号）。

### 2.2 文档鉴别材料

登记要求：

- 可以是用户手册、操作说明书或设计说明书，本项目有操作界面，提交**用户手册**
- 每页不少于 30 行（含图片的页面可豁免）
- 前、后各连续 30 页，不足 60 页则全部提交
- 封面标注软件全称、版本号、著作权人，须与申请表一致
- 页眉标注软件名称，页码标注在右上角
- 有界面的软件必须含操作步骤截图

`用户手册.md` 已按此要求撰写完成，共 12 章加 3 个附录，覆盖软件概述、运行环境、安装部署、快速开始，以及论文精读、论文库、代码分析、工作区、深度研究、系统设置六大功能模块的逐项操作说明，另含快捷键表、常见问题与接口一览。

脚本自动生成封面与目录，并把 Markdown 中的 `【截图 x-x】` 渲染成带边框的占位框和图题。

## 三、申请流程

### 第 1 步　实名认证（1–3 个工作日）

访问 `https://www.ccopyright.com.cn` 注册账号，进入个人中心完成实名认证。个人上传身份证正反面，单位上传营业执照。

**这一步有审核等待期，建议最先做**，与准备材料并行。

### 第 2 步　准备材料

按第二节产出四项材料。源程序与用户手册用本目录的脚本生成，主体证明自备，申请表在第 3 步于线上填写。

### 第 3 步　在线填报

登录后选择「计算机软件著作权登记」，按 `申请表填写指引.md` 逐字段填写，上传源程序与用户手册文档。

**填报时反复核对的三项**：软件全称、版本号、著作权人。这三项在申请表、源程序页眉、用户手册封面与页眉四处出现，必须逐字一致，包括标点与空格。不一致是最常见的补正原因。

### 第 4 步　等待受理

提交后约 1–2 周下发受理通知书。

### 第 5 步　实质审查

依《计算机软件著作权登记办法》第二十条，登记机构自受理之日起 60 日内完成审查。实践中一次性通过、无补正的情况约 1–2 个月下证；有补正则顺延。

### 第 6 步　领取证书

审查通过后可选择电子证书或纸质证书。

**整体周期预估：实名认证 1–3 个工作日 + 材料准备 1–2 天（本项目主要耗时在截图）+ 受理 1–2 周 + 审查 1–2 个月。**

## 四、软件名称与版本号

### 4.1 名称

代码库中的项目名为「论文精读助手」。软著登记对名称有习惯性要求：应简短明确、指向清晰，习惯以「软件」「系统」「平台」结尾。

**建议全称：论文精读辅助分析软件**

「助手」结尾并非不能通过，但改为规范结尾可减少被要求补正的概率。名称一经登记不便更改，且必须与文档四处标注一致，请在提交前确定，然后统一替换本目录所有文件中的占位。

名称的硬性限制：不得违反宪法和法律，不得损害国家和公共利益，不得违背公序良俗。

**简称**：没有就留空，不要填「无」，也不要与全称相同。本项目建议留空。

### 4.2 版本号

申请表的版本号习惯用两段式：`V1.0`。代码库的 `v5.2.0` 是三段式，不符合填表习惯。

**建议填写：V1.0**

理由：登记的是**当前提交的这一个版本**，不是迭代历史。填 `V5.2` 并无不可，但审查时可能被问及前序版本是否已登记、是否已发表，徒增沟通成本。首次登记填 `V1.0` 最省事。

确定后需同步修改：

- `gen_source_doc.py` 与 `gen_manual_docx.py` 的 `--version` 参数
- 申请表的版本号字段

注意：前端 `package.json` 中的 `5.2.0` 是软件自身的迭代版本号，与软著登记版本号是两套编号，**不需要为了软著去改动代码库版本号**。

## 五、需要你确认的事项

以下三项无法从代码推断，只能由你确认后填写。

### 5.1 著作权人

- **个人申请**：著作权人填本人姓名，提交身份证复印件
- **单位申请**：著作权人填单位全称（与营业执照一致），提交营业执照副本复印件

### 5.2 是否构成职务作品

如果本项目是在校期间使用学校资源完成、属于导师课题成果，或是在职期间属于本职工作任务，则可能构成职务作品，著作权人应为单位而非个人。

这一判断影响权利归属，填错会导致证书主体错误。若存在任何不确定，建议先与所在单位或学校的科研管理部门确认。

### 5.3 发表状态

代码仓库当前为**私有**，未向公众提供复制件、未发布产品、未上线对外服务，因此可填「**未发表**」，并且**不需要公开源代码**。

但如果曾经把软件提供给他人使用、做过公开演示或部署过对外可访问的服务，则属于已发表，需如实填写首次发表日期。填报不实会影响登记效力。

## 六、风险提示

### 6.1 PyMuPDF 采用 AGPL-3.0 许可（需关注）

后端 PDF 文本抽取的主路径依赖 PyMuPDF，其许可为 AGPL-3.0。这是本项目全部依赖中**唯一的强 copyleft 许可**，其余依赖（FastAPI、React、PyTorch、ChromaDB、sentence-transformers、Mermaid、xterm.js 等）均为 MIT、Apache-2.0 或 BSD 等宽松许可。

**对软著登记本身没有影响**——登记是形式审查，不核查依赖许可。

**对后续商用或对外分发有影响**：AGPL-3.0 具有传染性，若通过网络对外提供服务，需按同一许可开源整个项目，或向权利方购买商业授权。

缓解成本很低：`backend/services/pdf_parser.py` 中已实现基于 pypdf（BSD 许可）的后备抽取路径，`_extract_with_pypdf` 与 `_extract_with_pymupdf` 是同一层接口的两个实现。若确定要规避 AGPL，将主路径切换为 pypdf 并移除 PyMuPDF 依赖即可，代价是部分复杂版式 PDF 的抽取质量下降。

**这是产品与商业层面的决策，不阻塞软著申请，可在下证后再处理。**

### 6.2 提交材料的敏感信息

源程序与用户手册中不得出现真实的接口密钥、密码、个人邮箱与真实用户数据。

已核查项：

- 源码全文扫描未发现硬编码的接口密钥
- `.env.example` 仅含占位值，且该文件不在源程序采集范围内
- 用户手册中所有配置示例均使用描述性占位文字

补截图时需再确认一次：设置页面的密钥字段务必保持掩码状态。

### 6.3 AI 辅助开发的独创性问题

**按你的要求，此项暂缓处理，留待其余材料齐备后再评估。**

此处仅作记录：本项目在开发过程中使用了 AI 编程工具协同迭代。中国软著登记为形式审查，不核查创作过程，实践中不影响下证；但申请表含「独立开发」声明，法理上纯 AI 生成内容的独创性仍存争议。

需要说明的是，本项目在架构设计与核心算法上有明确的人类设计决策——`graphkit/relatedness.py` 的八通道关联度融合、`graphkit/calibration.py` 的权重自监督校准、`graphkit/backbone.py` 的目标密度反解，这些是可主张独创性的实质部分。

另需注意：提交的源程序不应包含 AI 协作配置文件（`CLAUDE.md`、`AGENTS.md`、`cc-iterate.sh`、`ITERATION_LOG.md`）。`gen_source_doc.py` 只采集 `.py` / `.ts` / `.tsx` / `.js` / `.jsx` 源文件，这些文件本就不在采集范围内。

### 6.4 缺少 LICENSE 文件（不影响申请）

项目根目录没有 LICENSE 文件。这不影响软著登记，但建议补充，以明确权利声明。

## 七、统计口径与复核

申请表需填写源程序量。本项目的取值与口径如下：

```
python3 docs/copyright/tools/gen_source_doc.py --stats
```

输出：

| 指标 | 数值 |
|------|------|
| 采集源文件 | 185 个 |
| 物理总行数 | 44,396 行 |
| 空行 | 5,466 行 |
| 剔除的无效注释行 | 439 行 |
| **有效代码行数** | **38,491 行** |
| 可排页数 | 826 页（每页 50 行） |

**采集范围**：后端 `backend/` 下的 `.py` 文件，前端 `frontend/src/` 下的 `.ts` / `.tsx` 文件。

**排除范围**：测试文件（`test_*.py`、`*.test.ts`、`*.spec.ts`、`tests/` 目录）、类型声明文件（`*.d.ts`）、依赖目录（`node_modules`、`__pycache__`）、构建产物（`dist`、`build`）。排除测试是因为软著提交的是软件本身，而非其测试脚手架。

**无效注释行的判定**：纯装饰性的分隔线注释（如 `# ------`、`// ======`）计为无效并剔除；承载语义的注释保留。需要更严格的口径时，加 `--strip-comments` 参数可剔除全部纯注释行。
