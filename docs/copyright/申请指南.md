## 二、权利情况（已确认）

申请人已确认以下事实，据此确定各项填报口径：

- 著作权人为**个人**，开发者仅本人一人
- 纯业余时间开发，与单位、学校、他人均无关
- 无任何商用经历
- 从未公开使用或传播，从未公网部署
- 未申请专利，未参加评奖或竞赛

**由此确定：**

| 填报项 | 取值 | 说明 |
|--------|------|------|
| 开发方式 | 独立开发 | 不需要合作开发协议 |
| 权利取得方式 | 原始取得 | 不需要转让合同或继承证明 |
| 是否职务作品 | 否 | 业余时间、未使用单位资源，著作权人为个人 |
| 发表状态 | 未发表 | 无需公开源代码，且后续需填写的内容更少 |
| 办理身份 | 我是申请人 | 验证码发本人手机，不走代理人流程，不需单位授权 |

这套组合是最简路径：不涉及任何第三方证明材料，全程个人可独立完成，0 费用。

## 三、需要提交的材料

登记为形式审查，材料齐备且格式合规即可受理。共三项：

| 序号 | 材料 | 状态 | 产出方式 |
|------|------|------|----------|
| 1 | 在线填报的申请表内容 | 需填写 | 字段取值见 `申请表填写指引.md`，已按字数限制定稿 |
| 2 | 程序鉴别材料（60 页 PDF） | **可自动生成** | `tools/gen_source_doc.py` |
| 3 | 文档鉴别材料（用户手册 PDF） | **已撰写，待补图与改写** | `用户手册.md` + `tools/gen_manual_docx.py` |

「其他证明材料」为空——独立开发不涉及委托或合作开发协议。

**两份鉴别材料最终都要提交 PDF，不是 Word。** 脚本生成 docx 后，在 Word 中「文件 → 导出 → 创建 PDF/XPS 文档」导出为**文本型** PDF（代码以矢量字嵌入），不要用截图拼成的图片型 PDF。

### 3.1 程序鉴别材料

登记要求：

- 提交源程序前、后各连续 30 页，共 60 页；不足 60 页则全部提交
- 每页不少于 50 行，不含空行与无效注释行
- **不要封面，第一页直接是代码**
- 页眉标注软件全称与版本号，须与申请表一致；页码在右上角
- 最后一页不能停在明显未闭合的语句上
- 不得混入依赖目录、锁文件、README、图片、配置文件
- 不得包含第三方版权声明、开源协议正文、第三方作者信息
- 不得包含用户数据、接口密钥等敏感信息

生成命令：

```bash
python3 docs/copyright/tools/gen_source_doc.py \
    --name "论文精读辅助分析软件" \
    --version "V1.0"
```

脚本把「每页 50 行」做成固定排版结果而非依赖 Word 自动断页：按显示列宽硬折行、精确行距、逐页硬分页。

**已验证的输出**：A4，60 页，每页 50 行，无封面首页即代码，页眉左侧为软件全称与版本号、右上角为自动页码域，文件之间有清晰的路径标题行，首页起于后端服务入口 `backend/main.py`，末页收尾于一个前端页面组件的自然结束处（右花括号）。已扫描确认文档中无接口密钥、邮箱、密码赋值，也无第三方版权声明或开源协议正文。

导出 PDF 前目视确认一次：页数正好 60、页眉页码正常、末页闭合完整。

### 3.2 文档鉴别材料

登记要求：

- 有操作界面的软件提交**用户手册**
- 每页不少于 30 行（含图片的页面可豁免）
- 前、后各连续 30 页，不足 60 页则全部提交
- 封面标注软件全称、版本号、著作权人，须与申请表一致
- 页眉标注软件名称，页码在右上角
- **必须含真实界面截图**，每个小标题对应的内容尽量都有截图
- 截图中的软件名称、版本号必须与申请表一致

## 四、申请流程

### 第 1 步　实名认证（1–3 个工作日）

访问 `https://www.ccopyright.com.cn` 注册账号，进入个人中心完成个人实名认证，上传身份证正反面。

**这一步有审核等待期，务必最先做**，与准备材料并行。

### 第 2 步　准备材料

按第三节产出两份鉴别材料，按第五节补图与改写。

### 第 3 步　在线填报

登录后进入业务办理，选「**R11 计算机软件著作权登记**」，身份选「**我是申请人**」。

按 `申请表填写指引.md` 逐字段填写。注意**字数限制是硬约束**：「软件的主要功能」必须 500–1300 字符，「软件的技术特点」≤100 字符，各环境字段 ≤50 字符。指引里的文案已实测字数，可直接粘贴。

上传两份 PDF，交存方式选「**一般交存**」。

### 第 4 步　提交与授权

确认信息后提交，本人手机会收到授权验证码。

⚠️ **验证码 1 小时内有效，期间不要刷新页面、不要关闭浏览器、不要断网**，否则整个填报流程需要重来。

### 第 5 步　签署申请表

系统生成申请表供下载。个人申请只需填右下角：**本人签名 + 身份证号**，不需要公章。扫描后上传。

关于表上可能出现的手抄承诺条款，见第六节。

### 第 6 步　等待受理与审查

提交后约 1–2 周下发受理通知书。依《计算机软件著作权登记办法》第二十条，登记机构自受理之日起 60 日内完成审查。

个人申请无需单位层层审批，周期明显短于单位申请。一次性通过、无补正的情况通常 1–2 个月下证；有补正则顺延，按补正要求修改后重新上传即可。

审查通过后发放**电子证书**，不涉及邮寄。个人申请全程 0 费用。

## 六、风险提示

### 6.1 文档鉴别材料的 AIGC 审查（当前最高风险）

据近期社区反馈，登记机构对 AIGC 内容的审查趋严，**已有申请人因文档鉴别材料被判定为 AI 生成而被要求补正**。相对而言，代码部分用 AI 编写未见因此被拒的报告；风险集中在文档鉴别材料。

本目录的 `用户手册.md` 由 AI 撰写。它的有利之处是内容基于对本项目前端代码的逐页核对，写的是界面上真实存在的按钮与文案，不是套用通用模板；但行文特征仍可能被识别。

**建议的处理方式：先截图，再照着截图逐节改写。**

先把 37 张截图截好，然后对着每一张图，用自己的话重写对应的那一节。这样写出来的文字会自然带上界面的具体细节和你个人的表述习惯，比在 AI 稿上做同义词替换有效得多。

改写时重点处理这些痕迹：

- 章节开头的概述性段落——这类段落最容易呈现模板感，建议直接删掉或改成一句话
- 高度整齐的排比与并列结构，各节字数过于均匀
- 「首先／其次／最后」「综上所述」「不仅……而且……」这类连接词的密集使用
- 每节都以相同句式开头

把现有的 `用户手册.md` 当作内容清单和结构骨架用——它保证了不漏功能点、章节层次符合登记要求；文字表述则请你自己过一遍。

### 6.2 界面旧项目名与版本号冲突（必须处理）

登记要求截图中的软件名称与版本号必须与申请表一致，且软件中不应出现旧项目名。本项目的界面存在两处冲突，且出现在几乎每一张截图里：

| 位置 | 当前显示 | 冲突点 |
|------|----------|--------|
| 顶部品牌区（每个页面都有） | `ER` / `EASY ESSAY` / `RESEARCH INTELLIGENCE` | 旧项目英文名 |
| 浏览器标签页标题 | `Easy Essay` | 旧项目英文名 |
| 终端面板（代码分析页） | `v5.2.0` | 与申请表的 V1.0 冲突 |
| 版本弹窗 | `V5.2.0` / `Easy Essay` | 两者皆冲突 |

`tools/screenshot_branding.py` 用于在截图期间临时把这四处切换到登记口径，截完用 `--restore` 还原。它只替换字符串字面量，不改动项目自身的版本管理逻辑，也不进入主线代码。

脚本会先检查这几个文件有没有未提交的改动，有则拒绝执行；`--restore` 通过 git 恢复。

> 本环境未安装前端依赖，无法完整验证切换后的编译结果。补丁只替换 JSX 文本与字符串常量，语法上是安全的，但建议你在截图前先跑一次 `npm run build` 确认。

### 6.3 申请表的 AI 承诺条款

新版申请表可能包含需**手抄**的承诺条款，内容涉及「未使用 AI」与征信承诺，需连同签名与身份证号一并填写。据社区反馈该条款曾出现又被撤下，各批次表单不一致。

**请以你自己下载到的那份申请表为准。** 如果表上确实有该条款，是否签署、如何签署由你本人判断——这是需要你签名承担责任的法律文件，我不替你做这个决定。

作为背景：本项目在开发过程中使用了 AI 编程工具协同迭代。同时，项目在架构设计与核心算法上有明确的人类设计决策——`graphkit/relatedness.py` 的八通道关联度融合、`graphkit/calibration.py` 的权重自监督校准、`graphkit/backbone.py` 的目标密度反解，这些是可主张独创性的实质部分。

另需注意：提交的源程序不应包含 AI 协作配置文件（`CLAUDE.md`、`AGENTS.md`、`cc-iterate.sh`、`ITERATION_LOG.md`）。`gen_source_doc.py` 只采集 `.py`/`.ts`/`.tsx`/`.js`/`.jsx` 源文件，这些文件本就不在采集范围内。

### 6.4 PyMuPDF 采用 AGPL-3.0 许可

后端 PDF 文本抽取的主路径依赖 PyMuPDF，其许可为 AGPL-3.0。这是本项目全部依赖中**唯一的强 copyleft 许可**，其余依赖（FastAPI、React、PyTorch、ChromaDB、sentence-transformers、Mermaid、xterm.js 等）均为 MIT、Apache-2.0 或 BSD 等宽松许可。

**对软著登记没有影响**——登记是形式审查，不核查依赖许可，且提交的源程序中不含第三方协议正文（已扫描确认）。

**对后续商用或对外分发有影响**：AGPL-3.0 具有传染性，若通过网络对外提供服务，需按同一许可开源整个项目，或购买商业授权。你已确认目前无商用经历、无公网部署，因此当前不构成实际问题。

若将来要规避：`backend/services/pdf_parser.py` 中已实现基于 pypdf（BSD 许可）的后备抽取路径，`_extract_with_pypdf` 与 `_extract_with_pymupdf` 是同一层接口的两个实现，切换主路径即可，代价是部分复杂版式 PDF 的抽取质量下降。

项目根目录没有 LICENSE 文件。不影响软著登记，但建议后续补充以明确权利声明。
